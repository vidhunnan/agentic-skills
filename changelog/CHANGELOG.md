## 2026-08-24

### Added
- **A skill that splits the released version from the build you're testing** (`06cc137`) — `version-manager`, generalised out of `reviz.tools`, where the two shared one number and a local pack moved what npm would publish next. The model it encodes is four ideas: **two tracks that are never conflated**, a **version surface** (every file carrying the number, checked for agreement), a **generated ledger** where each candidate row names the release it targets and each release row names the candidate that became it, and a **profile** per artifact type. The profile catalog is the part that makes it reusable rather than npm-shaped — npm, Claude Code plugins, **Docker**, PyPI, binary/CLI releases, deployed sites, editor extensions, mobile apps, plain exports, and an interviewed **unknown** that says plainly when the catalog didn't cover a repo. Two rules were generalised out of the profiles rather than repeated in each: **a moving tag is not a version** (Docker's `:latest` and npm's dist-tags are pointers, so the ledger records the digest or exact version beside them), and **the two-number case is not an exception** — iOS/Android's marketing-version plus build-number pair is the released/candidate split with both halves given a field, so it maps rather than special-cases. It ships **the library's first supporting file**, `references/profiles.md`: ten profiles inline would have buried the skill, `CLAUDE.md` already permitted it, and the zip builder walks the folder, so it reached Claude.ai without a change. The skill also states what it does **not** own — `changelog/commits/` and `CHANGELOG.md` are `changelog-tracker`'s — because two skills now write the same folder.
- **This repo's own versioning policy, and the ledger under it** (`55ebabc`) — the new skill, run here. **Per-skill versions, bumped only when that skill changes**: each installs on its own, so a library-wide bump would tell someone reinstalling `branch-naming` that something changed in a skill they don't have. That is why `handoff-generator` sits at `0.5.0` and everything else at `0.1.0`, and why the numbers should stay uneven. `docs/VERSIONING.md` draws the distinction the repo actually needed — `plugin.json` is the only file carrying a version, so *version agreement* is trivial, while the marketplace entry, `skills.ts` and the README row carry none and need a **registration** check instead; conflating the two would have made three-quarters of the surface noise. The check was run before the policy was written: **fifteen skills, zero drift**. `changelog/VERSION-LOG.md` starts today with a baseline read from disk and **backfills nothing** — there are no tags and no prior release log, so it says the record begins here and states outright that the reasoning behind `handoff-generator`'s four bumps is not recoverable, rather than reconstructing four plausible entries nothing could check.
- **The fork behind the versioning policy, written down** (`6bbbd5b`) — ADR 0026. Fourteen skills sat at `0.1.0` and `handoff-generator` at `0.5.0` with **no record anywhere of why**, which is the condition this tier exists for. Both losing options are argued for before they are dismissed: **one library-wide version** gets its real advantages stated — one number, one row per release, no two skills disagreeing about what "current" means — and loses on one specific thing, that a user reinstalling `branch-naming` would see a bump caused by a design skill they never installed; **per-skill versions with no baseline row** loses because today's numbers are the only surviving record of what shipped before today. The consequences name the cost twice: **there is no "version of agentic-skills"** anyone can cite, and a cross-cutting change now means fifteen bumps in one commit. The careful part is the Rationale line — the owner **selected** this option from three, so the reasoning recorded is the reasoning that was *presented with* it, not wording they supplied. Writing "the owner argued that…" would have been a small, plausible, unfalsifiable fiction of exactly the kind [0014](../docs/decisions/0014-never-invent-a-rationale.md) forbids. It also corrects the README's ADR count, which claimed **21 when 25 existed** — a public page stating a number it cannot source, which is the defect the site's committed counts were built to stop.

### Changed
- **`node_modules` and the generated context graph stop showing up in `git status`** (`eeb3d46`) — three untracked artifacts had no rule covering them: a **new root `node_modules/`**, and `.graph-context/` plus `GRAPH.md`, both **generated** by the context-graph tool (`viz.json` is a 130KB derived index; `GRAPH.md` opens with a `<!-- BEGIN graph-context:graph -->` marker and reports 167 documents, 133 fragments and 423 edges read back out of the repo). Committing either would put a second, staler copy of the context stack next to the tiers that *are* the record. `node_modules/` is written **once, unanchored, for the whole repo** rather than as a second per-directory line — and the old `website/node_modules/` entry goes, because it was already redundant twice over: the root file now covers it, and `website/.gitignore:2` covered that subtree independently all along. `GRAPH.md` is ignored **by exact name, not as a pattern**: it sits at the root beside `README.md` and `CLAUDE.md`, and a `GRAPH*`-shaped rule is one that silently swallows a hand-written doc someone adds later. Nothing under any of the three paths was ever tracked — `git ls-files | grep -c node_modules` returned `0` first — so this is a status-noise fix with no `git rm --cached` and no chance of un-tracking something depended on. **`package.json` and `package-lock.json` are deliberately left alone**, untracked and un-ignored: they pin the tool that generates the graph, which is normally worth committing precisely *because* it is not the output, and that call belongs to the owner rather than to a commit about ignore rules.
